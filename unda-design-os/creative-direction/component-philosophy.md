# 8. Component Philosophy

Components are not designed as one-off visuals; each carries a philosophy that any designer can apply consistently. Detailed specifications belong in [`../design-system/components/`](../design-system/components/index.md) (Phase 3) — this section defines the intent each component must satisfy.

| Component | Intent |
|---|---|
| Cards | A container for one idea, never a catch-all. Structure and whitespace separate cards — not shadow or border weight. |
| Buttons | One primary action per view, stated in a verb. Secondary actions are visually quieter, never visually competitive. |
| Forms | Ask for the minimum. Validate inline and specifically — never with a generic error at the top of the form. |
| Pricing | Transparent by default. One plan may be recommended through typographic emphasis, never through an aggressive visual frame. |
| FAQ | Answers real objections, in plain language, not marketing copy disguised as a question. |
| Testimonials | Specific results from named, attributable people. A vague quote with a stock headshot undermines more trust than it builds. |
| Hero sections | States what the visitor gets, in one sentence, before it states anything about the company. |
| Case studies | Framed as problem → approach → measurable outcome — never as a portfolio gallery of finished screens. |
| Navigation & footer | Utility first. The footer is a sitemap and legal record, not a second marketing surface. |
| Tables & documentation | Set in Geist and Geist Mono for data; scannable first, complete second. Docs read like reference material, not prose. |
| Travel cards | The one component allowed to lead with imagery — a destination or itinerary is sold on feeling first, detail second. |
| Dashboards | Show the number that matters most at the largest size on the screen; everything else is supporting detail, deliberately smaller. |
